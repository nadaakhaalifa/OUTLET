# ADR-0057: Per-store branding as a typed, versioned theme document with platform-locked trust elements; read-only "Preview as customer" with a server-computed readiness checklist

- Status: **Proposed** (owner decisions O1 to O10 and VR-ST-01..07 open; nothing is built)
- Date: 2026-10-18
- Deciders: Owner (tier mapping, PDP reach, custom fonts, fixed schemes, cover video, ranking effect), Counsel (font licences, trademarks, CPL presentation, child imagery, App Store), Design (font and preset curation), Architect (model). Security review of the upload and font pipelines before enabling uploads; chief-reviewer at milestone sign-off.
- Spec: `docs/specs/store-branding-and-preview.md`
- Spec refs: master prompt 3, 4, 5, 9, 10, 19, 25, 27, A2.13, B5, B7, T2, T5, T10
- Related: ADR-0056 (entitlement `storefront.customisation`, `store_restrictions`, fail-closed entitlements), ADR-0051 (no external AI vendor: moderation and OCR ports Unconfigured), ADR-0055 (guest persona), ADR-0054 (iPad zoom), ADR-0028 (kill-switch polarity), ADR-0045 / ADR-0052 (release rules for seller analytics used in impact estimates)

## Context
The owner wants each brand to give its store a fully distinct identity (colours, fonts, shapes, vibe), e.g. a pastel, soft baby shop next to a sharp, elite luxury label, and a button for the brand to inspect its store as a customer sees it, with a list of what to fix. Today all UI reads one platform token set (`packages/ui-tokens`), fonts are bundled at build time, the kit `PriceBlock` and badges carry the legally sensitive price and discount display (spec 9, CPL 181/2018), and there is no storefront editor, preview or listing-quality score.

## Decision
1. **Theme = typed data, not code.** A Zod-validated theme document (8 palette roles per scheme, curated Arabic+Latin font pairing, display scale, radius, density, motion mood, imagery, logo/wordmark/cover asset ids, AR/EN tagline, up to N typed sections) compiled by the platform into tokens and applied by a scoped `StoreThemeProvider`. No CSS, markup, URLs or font names from sellers. Presets are pre-filled documents.
2. **Platform-locked elements never read store tokens**: price block, discount and VRP labels, verified and price badges, "Sponsored", Plus, stock lines, ratings, size recommendation, delivery and return lines, seller legal identity, commerce CTAs, legal links. Enforced by a lint rule (`DS-THEME-LOCKED`), reserved card slots, adversarial-theme contract tests and visual regression. Bag, checkout, orders, returns and cross-store surfaces are never themed. Brand assets and taglines may not contain price, discount, scarcity, timer, verified or rating claims.
3. **Accessibility guard**: every colour pair in both schemes checked against WCAG 2.2 AA (4.5:1 text, 3:1 non-text, cover text with scrim); failing publishes are refused with a suggested nearest passing colour (OKLCH lightness search, hue preserved) that the seller must accept explicitly; never silently altered.
4. **Versioning**: immutable `store_theme_versions`, one draft per store with `If-Match`, publish = atomic live-pointer move + outbox event, rollback = pointer move to an earlier version; gates: schema, approved assets, contrast, entitlements, no `no_custom_theme` restriction, kill switch.
5. **Fonts**: curated allow-list only (openly licensed families, licence file stored, sanitized, subset, content-addressed on the platform CDN), downloaded on demand by the app, SHA-256 verified, disk LRU, max 300 ms wait on first visit then platform fonts with no mid-view swap. Seller font uploads off (O3).
6. **Assets**: presigned upload to quarantine, raster only (no SVG/GIF/PDF), sandboxed decode, AV scan, metadata strip, re-encode, pHash impersonation and restricted-mark checks; moderation and OCR ports Unconfigured at launch, so every asset is human-reviewed by Trust and Safety until in-house models exist.
7. **Entitlements** extend ADR-0056 (`storefront.customisation` plus typed keys for palette, fonts, fixed scheme, PDP band, cover video, max sections, preview states); tier mapping is owner decision O1; preview and the readiness checklist are never tier-gated; downgrade never deletes a theme.
8. **Preview as customer**: the in-app preview (real shopper code on the brand's own device) is the source of truth; the Seller Center preview uses react-native-web if a spike succeeds, else a parity-tested DOM renderer with an "approximation" note and a QR hand-off to the phone. Preview tokens are short-lived, store-bound, audience `store_preview`, accepted only on an allow-list of GET routes, excluded from analytics, ranking and Buy Box inputs; personas are synthetic; simulated states are watermarked and never reachable by shopper tokens. Admin "inspect as customer" needs a reason code and is audited.
9. **Readiness checklist**: server-computed listing quality score and store readiness score (weighted pass ratio, blocker cap, alpha mix of catalogue and store checks), admin-configurable in effective-dated, two-person-approved config versions; impact shown only from real, releasable data; display only in v1 (no ranking effect until O6).
10. **Kill switches** `kill.storefront.theming`, `kill.storefront.fonts`, `kill.storefront.asset_uploads` (true allows, default blocked) and flags `flag.storefront_theming`, `flag.store_preview`, `flag.listing_readiness`; per-store restriction `no_custom_theme`.

## Options compared
- **Theme expression.** (a) Seller templates/CSS/remote components: maximal freedom, but code-like (App Store risk), unbounded security review, cannot guarantee locked elements. (b) Presets only: safe, cannot make brands feel distinct. (c) Typed document with presets inside: chosen; data only, one renderer, honesty enforced structurally.
- **Font delivery.** (i) Bundle all: instant, but app size and a release per change. (ii) On-demand, hash-pinned, cached: chosen; bytes only for visited stores. (iii) Seller uploads: licence and malware risk; deferred to O3.
- **Contrast failures.** Reject only (frustrating), silent auto-fix (changes brand colours without consent), suggest-and-accept: chosen.
- **Web preview fidelity.** react-native-web (same code, needs a spike), separate DOM renderer (drifts), simulator screenshots (exact but slow and costly): in-app preview is exact; web takes the first that passes the spike, with the DOM renderer as the fallback.

## Owner and counsel decisions (block acceptance)
O1 tier mapping of storefront entitlements · O2 theme on PDP (brand band) or store page only · O3 brand-proprietary font uploads · O4 fixed light-only or dark-only stores · O5 cover video · O6 readiness score effect on ranking, Health Score or visibility · O7 human review of all assets vs sampling · O8 final font families and presets · O9 platform staff inspect-as-customer · O10 notice before readiness config changes. Counsel and engineering VERIFY: VR-ST-01 font licences, VR-ST-02 seller-uploaded marks, VR-ST-03 CPL presentation and identity fields on branded pages, VR-ST-04 App Store (themes and fonts as data), VR-ST-05 child and personal imagery in assets, VR-ST-06 Expo SDK 57 runtime font registration, VR-ST-07 react-native-web feasibility.

## Consequences
- New API module `storefront`, pure code in `packages/ui-tokens` (contrast solver, compiler) and `packages/domain/src/storefront` (readiness), new tables (themes, versions, assets, fonts, pairings, presets, events, preview sessions, quality config and snapshots) with RLS and `data_inventory.yaml` tags, an upload worker and a font ingestion tool.
- The kit gains a provider, a locked capsule and reserved card slots; a new design lint rule joins `tooling/design/rules.mjs`; the debt baseline must not grow.
- The API gateway gains a token audience with a GET allow-list; analytics ingest must drop preview traffic.
- Trust and Safety gets an asset review queue whose load is human-only until in-house moderation exists (ADR-0051).
- Every number in the spec is a default; weights and thresholds are admin data; no plan price or tier name is set.
