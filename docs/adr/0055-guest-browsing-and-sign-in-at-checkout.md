# ADR-0055: Guest browsing with a device-only bag and saved items; account required only at checkout (overrides master prompt §6 "Guest bag is not supported" and the onboarding-first order of §1)

- Status: **Accepted** for the product direction (owner instruction, 2026-10-16). The legal points in "Proposed" below are **Proposed** and gate production: the feature ships behind `flag.guest_browsing`, off in production until VR-GUEST-01 and VR-GUEST-02 are closed.
- Date: 2026-10-16
- Deciders: Owner (direction), Architect (design); Counsel and DPO (Proposed section); chief-reviewer checkpoint on the merge endpoint (auth and personal data)
- Spec: `docs/specs/guest-browsing.md`
- Spec refs: master prompt §1, §2, §6, §7, §8, §12, §13, B1, B6, B7; `docs/specs/cart.md`; `docs/specs/auth-production.md`; `reports/Viral feed onboarding checkout reviews.md` §C (it proposed "ADR-0045"; that number is taken by the dashboard read path, so this is 0055)
- Related: ADR-0053 (checkout step pages, unchanged), ADR-0002 (residency, unaffected: no guest data reaches the server), VR-10 (Apple), VR-DASH-07 (attested ingest)

## Context
The owner said: "Don't take me to create account; let me browse, add to favourites, add to cart and everything; only before I buy ask me to create an account." Today the first run goes region → role → `/onboarding/account` (DOB, 18+, terms, phone, OTP, consents) before any browsing (`features/role-choice/model.ts` `resolveEntry`), and every cart and wishlist route needs a shopper bearer. The master prompt §6 says "Guest bag is not supported: an account is required (18+ gate)", and `docs/specs/cart.md` repeats it. CLAUDE.md makes the master prompt the source of truth unless the owner overrides it; this ADR records that override.

## Decision
0. **Owner rule R0: sign-up only at the Checkout gate.** The only place a guest is ever asked to create an account, or shown the sign-up flow (DOB, 18+ box, phone or provider, consents), is the moment they tap Checkout in the Bag, before Delivery. No other screen, banner, nudge, badge, interstitial, onboarding step, role-chooser path, empty state or modal may do so. A dependency-cruiser rule, a source-guard test and a Maestro walk enforce it (spec §13).
1. **Signed-out shoppers browse as guests; first-launch screens appear once.** First launch only: region screen (device-only, Egypt selectable, others "Not available yet", no "notify me", no location permission) → entrance page → Home as a guest. Every later launch opens Home directly (`resolveEntry`: blocked, brand, region not chosen, role not chosen, else `/(tabs)`). Region is changed later in Settings → Region without sign-in or restart; the brand path is reached later through a quiet "Sell on Z-OUTLET" row in Me and Settings.
2. **Guest state is device-only.** Bag, saved items, recently viewed and affinity counts live in an `expo-sqlite` database (`outlet-guest.db`) behind a `GuestStorageAdapter` port. `expo-sqlite` is "Included in Expo Go" in the SDK 57 reference; MMKV is not used now (dev-client only) but can be swapped in behind the same port. The store is **not encrypted** (SQLCipher is "not supported on Expo Go") and holds no PII: ids, quantities, timestamps, public catalogue text and a merge idempotency key. The install id and tokens stay in SecureStore. A strict schema plus a forbidden-field test keeps PII out. Caps are the server's (50 lines, 10 units per SKU); TTLs (owner accepted) are bag 30 days idle, saved 180 days, viewed 30 days. Guests make no server writes; they read public routes only.
3. **Account-bound features are quiet for guests, never prompts.** Each is hidden (wallet, rewards, referral sharing, review writing, list sharing, saved-search alerts, addresses), an honest empty state with no sign-up link (orders: "Your orders will appear here after your first purchase"; live drops), device-local (size profile in SecureStore, price and stock alerts in the guest store), or deferred to checkout or to after the first purchase (Plus, gift-card redemption, vouchers, COD, BNPL inside checkout; gift-card buying, stylist, budget, notification permission after the first order). One table, `features/guest/capabilities.ts`, drives every entry point. Nothing is held for a guest: stock holds and the price lock still start at `POST /v1/checkout`.
4. **Checkout gate (unchanged content)**: age attestation (DOB + unticked 18+) first for every method, because the server requires a passed `/v1/auth/age-gate` before OTP, Apple, Google and passkey (returning users re-enter the DOB on a new device; owner accepted); then phone OTP, Apple, Google or passkey; then, for a new account, consents with every purpose off. Then merge and continue exactly at checkout step 1 (Delivery). `AccountCreateScreen` is reached only from the gate.
4b. **Quiet sign-in for existing accounts, not a create-account prompt.** A text action "Sign in" in Me and on the entrance page, mode `existing_only`: no consents step, no create option; an unknown identity gets "We couldn't find an account for this number" and nothing is created (API gap G-9). Success merges the guest bag with the same larger-quantity rule.
5. **Merge** goes through one new idempotent endpoint, `POST /v1/me/guest-merge`, in one transaction: union by SKU, the larger quantity wins (owner decision; guest 2, account 3 → 3, never 5), clamped, live server prices, overflow and unavailable items moved to Saved, recently viewed accepted only with `personalization` consent. The device store is cleared only after a 200.
6. **No true guest checkout.** Every order still belongs to a verified-phone account (one account per phone, DSAR, deletion, BOLA, returns and referrals depend on it).
7. **Guests get no server personalisation**: public routes only, `personalized=false` where it exists; device-only re-ranking from local signals.

## Options compared
| Option | Complexity | Accuracy and safety | Cost | Scalability |
|---|---|---|---|---|
| **A. Device-only `expo-sqlite` store behind a port + merge endpoint (chosen)** | Medium: storage port, two guest ports, one endpoint | High: no pre-account personal data on the server; server prices and caps on merge | Low: works in Expo Go, no new token audience or purge job | Good for the app; a future shopper-web guest needs its own decision |
| A2. Same, but MMKV (encrypted) | Medium | Same, plus encryption at rest | Needs a dev-client build (not Expo Go) | Same; kept as a later adapter |
| B. Anonymous server session (anon token, server bag) | High: new audience in `packages/policy`, anon minting with App Attest, purge job, merge | High, but adds a pseudonymous server dataset whose PDPL status is unverified | Medium-high | Best: cross-device, works for web |
| C. Keep account-first (status quo) | None | Highest legal certainty | None | Fails the owner's request and the 5.1.1(v) spirit |
| D. True guest checkout (orders without an account) | Very high | Breaks one-account-per-phone, DSAR, BOLA, returns and referrals | High | Poor |

For account-bound features, one sign-in sheet with a per-feature reason (the common pattern) was rejected by owner rule R0 in favour of quiet hidden, empty, local or deferred behaviour. A wins on cost and privacy for an iOS-first launch; B is the upgrade path if shopper web needs guests (new ADR). For merge transport, replaying existing routes was rejected: 50 lines exceed the 60/min cart limit, it is not atomic, and wishlist item add is not idempotent.

## Consequences
- Positive: no registration before value; conversion friction moves to the moment of purchase; the checkout saga is untouched.
- Negative: no cross-device guest bag; data is lost on uninstall (stated in the UI); the store is plaintext in the sandbox and in device backups (no PII); guest prices need public reads (a SKU batch route is added); stylist, budget and gift-card buying stay invisible until the first purchase, because R0 forbids prompting for them.
- Work: API gaps G-1…G-9 and work packages G0…G5 in the spec, starting after round-2 WP-2…WP-6 merge.
- Docs to amend in WP-G0: master prompt §6 note, `docs/specs/cart.md`, `docs/specs/wishlists.md`, `docs/specs/auth-production.md`, `data_inventory.yaml`, the verify register and the ADR index.

Whether an 18+ marketplace may let unverified visitors browse and build a local bag, and whether the notice wording suffices. Also whether an under-18 block must keep blocking browsing (default: yes, as today).
- **VR-GUEST-02 (DPO):** whether the unencrypted on-device store (no PII; analysis in spec §5) is proportionate under the PDPL security duty, or a dev-client encrypted adapter (SQLCipher or MMKV, key in SecureStore) is required before launch; the PDPL status of the device-only store and of a device install id ("online identifier", Art. 1); whether a guest analytics banner is allowed or guests should send no analytics until account creation; whether the banner choice may be shown as the account `analytics` toggle state; RoPA and privacy-notice wording. Default: no guest analytics leave the device until anonymous attested ingest exists and the DPO agrees.
- **VR-GUEST-03 (Product / Legal, extends VR-10):** the current App Store 5.1.1(v) text, and confirmation that requiring an account to place an order (not to browse) is acceptable; Sign in with Apple parity when Google ships.
- **VR-GUEST-04 (Counsel):** sign-up, age attestation, Terms acceptance and consents happen only at checkout (R0). Is that point acceptable: Terms bind before the purchase, and the consents and 18+ rule are not presented earlier than the first order?
- **VR-GUEST-06 (Security / Legal), tracked blocker before real users (not before staging):** the 180-day recycled-number step-up is not implemented in either OTP mode, so a correct code on an unseen device issues a full session. In sign-in-only mode the age gate still precedes the OTP request (item 4, accepted by the owner).

## Implementation note (WP-G0, API, 2026-10-17)
Built dark behind `flag.guest_browsing` (platform `GUEST_BROWSING_GATE`, default blocked, 404): `POST /v1/me/guest-merge` (module `guest-merge`, pure planner `packages/domain/src/cart/guest-merge.ts`, migration 0097 widens `cart_lines.source` with `merged_guest`) and the guest-only reads `GET /v1/public/skus`, `/feed`, `/home/banners`, `/search/suggestions`. G-8 already held: `free_delivery_threshold` is on `GET /v1/public/stores/{id}` (not on the list summary). G-6 (anonymous ingest) is NOT built (VR-DASH-07). Owner rule, tested: a guest never causes a server write except the merge after sign-up at checkout.

Deviations from the master prompt (the prompt itself is not edited): section 6 "Guest bag is not supported" (now: device-only guest bag, server bag still account-only); section 1 onboarding-first order (browse first, DOB/consents at the gate); B6 row 1 split (VR-GUEST-01); section 8 server-only wishlists for signed-out users.
Deviations from the spec text: event is `cart.guest_merged` (not `cart.merged`); a suspended-store line is dropped (spec section 3), not moved to Saved; `recently_viewed` is recorded after the commit and is best effort (`not_recorded` when the history write fails); no audit row (no PII; counts-only outbox event); G-3 has no cursor (the feed ranks one bounded pool); G-2 serves no verified-claim fields; rate limits use the device bucket plus a 4x IP bucket (the guard cannot yet choose a stricter IP bucket for unattested callers); 413 for over-cap arrays is checked before Zod. The 20/day merge limit is keyed by session (not user): the shared rate-limit guard keys counters by route and dimension only, so two windows on one dimension would share a counter (latent, affects stylist chat too; not changed here because stylist tests depend on it).

### Device bucket is not a security boundary (chief-reviewer finding 5)
`x-device-id` (and the install id in a body) is an UNATTESTED client header: a caller can omit or rotate it. The `device` bucket on the guest public reads only fairly splits carriers that share an IP (Egyptian CGNAT); the per-IP bucket (4x the device limit) is the real limit and applies to every request, with or without the header (tested). Only an attested token (App Attest, G-7, blocked with VR-DASH-07) can make the device bucket a boundary. `kill.public_catalog` also gates /feed and /home/banners (503 when blocked), like /skus and /search/suggestions.
Merge concurrency: the Postgres unit of work takes `pg_advisory_xact_lock(hashtext(user_id))` first, so two simultaneous first merges of one account cannot both create the default list of an intent. A raised quantity keeps the line's `price_at_add` and add time (the "price changed since you added" baseline); only qty and state change.

Rate-limit note (chief-reviewer): the `device` bucket on the guest public reads is keyed by the `x-device-id` header (or the attestation header), which is UNATTESTED and trivially rotated by a client. The IP bucket (4x the device limit) is the real limit; a request without the header is still IP-limited (tested). Only an attested token (G-7, VR-DASH-07) would make the device bucket a trust boundary. The merge serialises per account with a Postgres advisory lock so two concurrent first merges cannot create two default lists.
G-9 (2026-10-18): `POST /v1/auth/otp/verify` accepts `mode: "existing_only"` (404 `no_account`, creates no user, device, session or token, consumes the OTP; 404 while `flag.guest_browsing` is blocked); default unchanged. Existence leaks only after a correct code (to the number's holder). The OTP request still needs the passed age gate (unchanged), so the quiet-sign-in client must run the age gate first; Apple, Google and passkey assertion still create accounts and need the same mode before the mobile client may offer them in quiet sign-in.
G-9 completion and VR-GUEST-06 (2026-10-18, API only): Apple, Google and passkey assertion accept `mode: "existing_only"` (Apple/Google: 404 `no_account`, nothing created; passkey never creates); a suspended account on Apple/Google create mode answers 403 `account_unavailable` instead of a 500. The recycled-number step-up is built in both OTP modes: no tokens, 403 `step_up_required` with an account-bound passkey challenge (options compared and rules in `docs/specs/guest-browsing.md` "Recycled-number step-up design"). Mobile step-up screen and the no-passkey recovery path remain open (owner decision); VR-GUEST-06 stays a blocker before real users until they ship.
