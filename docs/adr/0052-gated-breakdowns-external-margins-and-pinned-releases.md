# ADR-0052: Shopper-gated breakdowns: external margins, one-dimensional release, pinned release ledger

- Status: **Proposed.** Amends ADR-0045 decisions 4, 4b and 4c. Changes a seller-facing privacy control and the utility of seller breakdowns, so it needs DPO acceptance together with ADR-0045 decision 4 (VR-DASH-02, VR-DASH-05; the distinct-visitor pinning touches VR-DASH-06). The pure core (`kanon-table.ts`) may be rebuilt to this design now; nothing is released while `release.seller_analytics.shopper_series` is blocked.
- Date: 2026-10-16
- Deciders: Architect (proposal), DPO (decision), Chief reviewer (checkpoint), Tech Lead
- Spec refs: `docs/specs/dashboard-foundations.md` track 4 ("Windows", "k-anonymity: one repository function, monotone suppression", tests), track 6 (memo DDL, erasure step 4); master prompt B1, 19.1 (k >= 50)
- Related: ADR-0045 (read path, decision 4 and 7), ADR-0047 (Cairo grid)

## Context and problem statement
The chief-reviewer found two High issues in the ADR-0045 suppression design, and checking the built core (`apps/api/src/modules/seller-analytics/domain/kanon-table.ts`) found a third.

1. **Wrong margin family.** The spec publishes a column margin (all dimension values in one bucket) only when it covers >= 50 shoppers and is not memo-hidden, and enforces complementary suppression only on lines whose margin it publishes. But the same column sums are released **ungated, at any window and grain** by `seller.traffic.*` views and `seller.sales.orders` (hour series compose any Cairo or UTC day or month). So `ungated total - shown cells = sum of hidden cells`, which may cover fewer than 50 shoppers. A memo-hidden column margin disables the check for that column entirely.
2. **The memo is monotone only for hidden aggregates.** A released cell is recomputed on every read. Erasure (which NULLs `shopper_key`, and the gated reader counts keyed facts only), late facts and distinct-count recomputation can change a released value, so two reads of the same cell differ by exactly the erased or late shoppers' contribution.
3. **The per-line rule is unsound even in one request.** With rows r1, r2, r3 and days d1, d2: a = (r1,d1) has 5 shoppers (primary). Row r1 then hides b = (r1,d2) (60 shoppers); column d1 hides c = (r2,d1) (70). Column d2's hidden set is {b}, union 60 >= 50, so its margin is published. Then `b = col(d2) - released(d2)` and `a = row(r1) - released(r1) - b`: a 5-shopper cell is disclosed. The current property test checks each line alone and passes. In a two-way table every hidden cell must avoid being a bridge of the hidden-cell graph, and sums of several cells need a full audit; per-line union counts are not enough.

## Decision
1. **External margins are always published.** Every additive shopper-gated (metric, dimension) declares in the registry the ungated metric that equals its column sum (`seller.traffic.views` by source -> the ungated view totals; `seller.geography.orders` by governorate -> `seller.sales.orders`). The release treats that column sum as published at every grain, whatever its shopper count or memo state.
2. **One-dimensional release for breakdowns (no internal margins).** Breakdown cells are released at **one fixed grain: complete Cairo months** (`dim_key`, month). The design publishes **no** row totals, multi-month totals or grand totals computed from gated cells. A "total" shown beside a breakdown is the ungated metric itself, labelled as such. With only external column sums, cells of different months are disjoint and the finer ungated sums cover every row, so the only derivable sums of hidden cells are per-month hidden sums and their combinations. Per column, the rule is: hidden set H is empty, **or** union(H) >= 50 distinct shoppers, **or** H is the whole column (its sum then equals the ungated total, which is already public). This is sound, and it also removes issue 3, because each cell sits on exactly one constraint. Day-grain breakdowns and row totals are dropped. Non-additive gated series (`unique_visitors`, `repeat_rate_bps`) keep day and month grains with primary suppression only: they have no additive relation, so complementary suppression does not apply.
3. **Pinned release ledger (the memo stores released values too).** Each aggregate (store, metric, dimension, `dim_key`, bucket) gets exactly one immutable ledger row: `hidden` (reason) or `released` (value). A released aggregate is always served with its pinned value. If the recomputed value differs, the pinned value is still served and the `seller_analytics_release_drift_total` counter increments. A pinned cell is never chosen as a complementary candidate, because it is already known. If a column is still unsafe after every not-yet-pinned cell is hidden, nothing new is released in that column and `seller_analytics_kanon_residual_total` increments. This can happen only after erasure lowers the union count of a hidden set that was released safely before; the response is then identical to the earlier one.
4. **Settle horizon for gated reads.** A gated bucket is released only once `now >= bucket_end + S` (S = 48 h by default; admin-editable with audit, minimum 24 h). Its cells read only facts with `ingested_at <= bucket_end + S`. Later facts still feed the ungated rollups and never change a gated value, so drift is limited to erasure.

## Options compared
- **Issue 1, margins.** (a) Keep two-way tables with row and multi-month totals, treat column sums as always published, and add an exact audit: a bridge-free hidden graph plus a check over derivable cell sets. (b) **Chosen:** one-dimensional monthly breakdowns with external column sums only. (c) Stop releasing the ungated totals per bucket. Option (c) is not workable, because sellers see their own orders and view counts elsewhere, and it does not fix issue 3. Option (a) keeps more utility but needs a non-trivial audit (an LP or lattice check of the tau-ARGUS kind) whose soundness is hard to prove. Option (b) is provably sound with a linear-time per-column rule. It costs per-day breakdowns and row totals.
- **Issue 2, recomputed releases.** (a) **Chosen:** pin released values in the ledger. (b) Re-hide any aggregate whose value changed. (c) Make the inputs immutable instead: a settle horizon plus values that count unkeyed facts, so erasure cannot change them. Option (b) still needs a stored value, loses cells steadily, and leaks a one-bit "something changed" signal. Option (c) stores nothing, but it relies on invariants, and distinct counts still fall on erasure. Option (a) is exact and fails closed. Taking (c)'s settle horizon as well keeps pinned values almost always equal to the truth.

## Consequences
- Breakdowns are monthly only, with no row totals. Sellers see per-day trends only for ungated metrics. The UI says "monthly; months with fewer than 50 shoppers per source are hidden".
- The ledger grows with every released aggregate as well as every hidden one. That is about 11 rows x 12 months per store, metric and dimension per year, which is negligible. It is purged with the facts at 25 months.
- A pinned aggregate keeps an erased shopper's contribution inside a released number that covers >= 50 shoppers. This is a DPO question under PDPL erasure; see below.
- `seller.geography.orders` cells can also be derived from the seller's own order access (buyer governorate on active orders). k-gating that breakdown therefore protects little against the seller. This is recorded for the DPO under VR-DASH-02.
- If the owner later wants day-grain or two-way breakdowns, that needs a new ADR with the exact audit (option 1a) and a chief-reviewer checkpoint.

## Owner decision required (DPO)
- Accept decisions 1-4 together with ADR-0045 decision 4 (VR-DASH-02, VR-DASH-05). Safe default: `release.seller_analytics.shopper_series` blocked and legacy behaviour unchanged.
- Accept that pinned aggregates covering >= 50 shoppers are not recomputed after erasure (VR-DASH-02). The same applies to pinned `unique_visitors` values (VR-DASH-06).
- Confirm the 48 h settle horizon.
