# Threat model 03: checkout, payments, ledger, refunds, store credit, payouts, reconciliation

Status: Draft for review · Date: 2026-10-11 · ASVS level: L3 · Spec refs: §7, §15, §B2, §B8, §T4, §20.2 · Code: `apps/api/src/modules/{cart,checkout,payments,ledger,refunds,store-credit,payouts,reconciliation,inventory}`, `packages/{domain,idempotency,outbox}` · Older detail (pre-code): `checkout-and-payments.md`, `ledger-and-payouts.md`, `store-credit-gift-cards-and-promotions.md`, `inventory.md`.

Chief-reviewer checkpoint required (money): this model is a draft input for that review, not a sign-off.

Evidence caveat: DB-level controls are proven on PGlite (WASM Postgres) in `*.pglite.test.ts`. `tooling/db/run-on-postgres16.sh` re-checks migration guarantees on a real PG16 cluster; it covers schema guarantees, not application race behaviour. Every PSP, courier and bank adapter is a fixture or fake (`payments/adapters/fake-provider.ts`, `paymob/fixture-transport.ts`); booted-in-production refuses fakes (`payouts/test/module-boot.test.ts`, `reconciliation/test/module-boot.test.ts`).

## Trust boundaries
App to API (`/checkout`); PSP to API (`POST /webhooks/{provider}`, `/webhooks/checkout/{provider}`); API to PSP; API to Postgres (ledger, outbox, inventory); finance staff to payout and reconciliation consoles; settlement files into reconciliation.

## Residual risk
- R-PAY-1: no real PSP, bank, or BNPL integration; all signature, settlement and refund semantics are fixtures. VERIFY BEFORE LAUNCH (VR-04, VR-05).
- R-PAY-2: no scheduler is wired in code for the integrity job, reservation sweeper, refund sweeper, payout runs or reconciliation (classes exist: `ledger/application/integrity-job.ts`, `inventory/application/lifecycle.ts`). Until a runner exists these controls do not run. Runbooks mark the commands as not available.
- R-PAY-3: no operator DLQ replay tool; outbox dead-letter column exists (`platform/db/outbox-store.ts`).
- R-PAY-4: wallet/closed-loop legal status is ADR-0003, VR-03 (counsel).
- R-PAY-5: mutation score >= 80% on ledger, refunds, reservation is a spec requirement; no Stryker run recorded for these modules (VERIFY `docs/plan` mutation reports).
