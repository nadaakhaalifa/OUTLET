# EAS build, update and release runbook (mobile)

Config: `apps/mobile/app.config.ts` (the only Expo config; app.json was removed) and `apps/mobile/eas.json`. Nothing here has talked to Expo, Apple or Google: the owner runs every account step.

## Owner decision before the first build (open question 9)
`IOS_BUNDLE_ID`, `ANDROID_PACKAGE` and `EXPO_SLUG` default to placeholders (`com.outletnk.placeholder`, slug `outlet-nk`). They cannot change after the first store upload. Set real values as EAS env vars (`eas env:create`) for every environment before the first store-bound build. Also set `APP_LINK_HOST` (universal/app links domain; placeholder, flagged, nothing is emitted while empty) and the two API URLs in `eas.json` (`REPLACE-...invalid`).

## Owner steps, in order
1. Enroll in the Apple Developer Program (organization needs a D-U-N-S number) and create a Google Play Console developer account (identity verification takes days; new personal accounts need the 12-tester/14-day closed test before production).
2. `cd apps/mobile && eas login` (existing z-outlet Expo account).
3. `eas init`. It writes the project id; with a dynamic config it may ask you to add it manually: put it in the EAS env as `EAS_PROJECT_ID` (config reads it for `extra.eas.projectId` and `updates.url`). Then `eas update:configure` is NOT needed (url is derived).
4. Set env vars per environment (`eas env:create`): IOS_BUNDLE_ID, ANDROID_PACKAGE, EXPO_SLUG, EAS_PROJECT_ID, APP_LINK_HOST.
5. Credentials: `eas credentials` (let EAS manage the iOS distribution cert and profile; Android keystore generated by EAS, back it up; enroll in Play App Signing).
6. First simulator build: `eas build -p ios --profile development` (dev client, simulator). Install on the simulator and run `expo start --dev-client`.
7. Internal preview: `eas build -p ios --profile preview` (needs registered devices: `eas device:create`) and `-p android --profile preview` (APK).
8. TestFlight: `eas build -p ios --profile production` then `eas submit -p ios` (create the App Store Connect app record first with the final bundle id). Add internal testers, then external after Beta App Review.
9. Play internal testing: first AAB must be uploaded manually in the Console once; later `eas submit -p android` (needs a service-account JSON, track `internal`).
10. Fill store metadata, privacy labels (`docs/compliance/app-privacy-labels.md`) and readiness docs, then submit for review.

## Xcode and local builds
SDK 57 / RN 0.86: the spec (T2) states Xcode 26 minimum for SDK 55+, and SDK 57 is newer, so assume Xcode 26+. This Mac has Xcode 16.4 (build 16F6): a local `expo run:ios` / `expo prebuild` + Xcode build is NOT expected to work; use EAS cloud builds (the macOS image has the right Xcode). VERIFY against the SDK 57 changelog (not found in local node_modules). Expo Go: cannot run this app reliably; it ships a fixed native module set, and we use `expo-updates` fingerprinting, config plugins (privacy manifest, localized permission strings, associated domains) and Reanimated/worklets versions that must match the binary. Use the development client build. Metro/web-only checks (`expo start`, `expo config`) work without Xcode.

## Staged OTA rollout (spec T2)
1. `eas update --channel staging --message "..."`; soak on internal builds.
2. Production: publish, then `eas update:rollout` (or `eas update --channel production --rollout-percentage 1`) and step 1% -> 10% -> 50% -> 100%, holding at least 2 h (1%) / 12 h / 24 h between steps, longer if traffic is low.
3. Automatic rollback criteria (any one, measured on the new update vs baseline in Sentry): crash-free sessions < 99.8% (SLO), crash-rate regression > 0.3 pp, checkout success < 99.5%, or any P1 incident. Action: `eas update:rollback` / `eas update:republish` of the previous group, then freeze. Automation (Sentry alert -> workflow calling the EAS API) is not built yet: until then rollback is a manual on-call step. Freeze updates 48 h before mega events.
4. Native changes (new fingerprint) always go through a store build, never OTA.

## What Expo supports for permission strings
- Localized `InfoPlist` strings: top-level `locales` map (done: `locales/ar.json`, `locales/en.json`) produces `InfoPlist.strings` per language; English stays in `ios.infoPlist` as the base. `expo-localization` plugin `supportedLocales` sets CFBundleLocalizations / Android locale config.
- Android has no per-permission rationale strings in config; runtime rationale text is in-app (i18n).
- `expo-blur` has no config plugin and needs no permission.
