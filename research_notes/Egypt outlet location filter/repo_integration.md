# Repo integration: governorate -> district filter for the outlet-shops list (read-only investigation)

Scope note: all findings come from local files (paths relative to /Users/nadakhalifa/OUTLET). No web sources were used, so there are no URLs. Each finding cites a repo file. Nothing was modified.

## Q1. Where do the Egyptian address structure and courier coverage live today?

### Takeaway
A canonical, bilingual, two-level (governorate -> city) Egypt location dataset already exists, but it is address/courier-oriented and has no district or neighbourhood level, no aliases and no status field. Its natural home is `packages/domain/src/addresses/coverage-data.ts` (seed) and the `coverage_*` tables (runtime). It is exposed in OpenAPI at `/v1/coverage/governorates` and `/v1/coverage/cities`.

### Cited Findings
- Spec: master prompt section 7 requires "structured Egyptian address (governorate -> city/district -> street, building, floor, apartment, landmark), validated against a courier coverage table" — `docs/haul-master-prompt-v3.md` (§7 Checkout, Flow step 1).
- Address spec: "Governorate and city must exist in the coverage tables (27 governorates, major cities, Arabic and English names; seeded from `coverage-data.ts`, admin-editable later). Unknown code => 400 `unknown_governorate` / `unknown_city`." Tables: `saved_addresses`, `delivery_snapshots`, `gift_address_tokens`, `couriers`, `coverage_governorates`, `coverage_cities`, `courier_coverage`. Routes `GET /v1/coverage/governorates`, `GET /v1/coverage/cities?governorate=` — `docs/specs/addresses.md` lines 9, 10, 17, 24. Seed coverage is an assumption pending VR-11 (line 30).
- Seed data file: `packages/domain/src/addresses/coverage-data.ts` (56 lines). Types `CityFixture = [code, nameAr, nameEn]` (line 7), `GovernorateFixture = [code, nameAr, nameEn, cities[]]` (line 8), const `GOVERNORATE_FIXTURES` (line 10). Header comment says codes follow ISO 3166-2:EG and the file is plain data with no imports so migrations can be generated from it. City codes are kebab slugs (e.g. `nasr-city`, `6th-october`, `el-gouna`). Also exports `COURIER_FIXTURES` (line 43: bosta cod=true, aramex cod=false), `COURIER_GOVERNORATE_EXCLUSIONS` (line 46), `COURIER_CITY_OVERRIDES` (line 52). Re-exported via `packages/domain/src/addresses/index.ts`. Cairo has 6 cities, Giza 5, Alexandria 4, etc. (only "major cities"; this is a fixture, not a full gazetteer).
- Actual DDL (migration `packages/db/migrations/0050_addresses.sql`): `coverage_governorates(code text PK CHECK ~ '^EG-[A-Z]{1,3}$', name_ar, name_en, position smallint)` (lines 25-30); `coverage_cities(governorate_code FK, code CHECK ~ '^[a-z0-9-]{2,60}$', name_ar, name_en, position, PK(governorate_code, code))` (lines 32-39); `courier_coverage(courier FK, governorate_code, city_code NULL, covered bool)` with unique index `courier_coverage_uq` on `(courier, governorate_code, COALESCE(city_code,''))` (lines 41-48); `saved_addresses.governorate_code`, `city_code` (lines 59-60). Seeds: governorates at line 140, cities at line 169, coverage at line 255. Read-only grant to `app_user` (line 50).
- Governorate ids look like `EG-C`, `EG-GZ`, `EG-ALX`, `EG-QH`, `EG-SHR`, `EG-DK`, `EG-BH`, `EG-FYM`, `EG-BA`, `EG-LX`, `EG-WAD`, `EG-SIN` etc. (from `coverage-data.ts` and exclusions).
- Pure logic: `packages/domain/src/addresses/rules.ts` — `CoverageEntry { governorateCode, cityCode|null }`, `evaluateCoverage(entries, governorateCode, cityCode)` (line 24) returns covered/not_covered/unknown; city-level row overrides governorate-level row. Address input fields `governorateCode`, `cityDistrictCode` (lines 59-60).
- API module: `apps/api/src/modules/addresses/` (`kysely-store.ts`, `ports.ts`, `service.ts`, `addresses.controller.ts`, `checkout-port.ts`, in-memory + pglite contract tests).
- OpenAPI: `/v1/coverage/governorates` (`docs/api/openapi.yaml` line 1818, op `listCoverageGovernorates`, scope `shopper:addresses.read`, `x-pii-class: P0`); `/v1/coverage/cities` (line 1865, query `governorate` pattern `^EG-[A-Z]{1,3}$`); schemas `CoverageGovernorateList`, `CoverageCityList` (lines ~33438-33460), `CoverageArea{code,name_ar,name_en,courier_coverage: covered|not_covered}` (line 33461); `AddressInput` uses `governorate_code` and `city_district_code` (line ~33490).
- Data-model docs disagree with the implementation (naming drift): `docs/data-model/fulfillment.md` lines 42-47 and 181 model `courier_coverage(governorate, city, district nullable, version)` with unique `(courier_code, governorate, city, district, version)`; `docs/data-model/users.md` lines 75-77 model `governorate_code, city_code, district`; `docs/data-model/inventory.md` line 33 and `docs/data-model/orders.md` line 141 use `governorate_code`/`governorate`. The shipped schema has no `district` column and no `version`. So "district" exists in the data-model docs only as a free/nullable field, not as a coded entity.
- Stores side: `docs/specs/stores-worlds.md` line 22 and 43 — `store_legal_identity_public` has `governorate` (free text); line 99: "`Store.legal_identity` in OpenAPI lacks `governorate` (B5 requires it)". Code: `apps/api/src/modules/stores/domain/store.ts` line 39 `LegalIdentity.governorate: string` (untyped string, not a coverage code). `docs/data-model/sellers.md` line 43 `text governorate`.
- Other places already keyed by governorate: `docs/data-model/promotions.md` line 60 (`target_type` includes GOVERNORATE), `docs/data-model/admin.md` line 134, `docs/data-model/recommendations-gateway.md` line 27 (feed filtered by courier coverage for default address), `docs/data-model/fraud.md` line 21.
- Mobile checkout already consumes the coverage endpoints: `apps/mobile/src/features/checkout/addresses-api.ts` and `apps/mobile/src/services/api-ports.ts` (`ApiAddressesPort` uses `listCoverageGovernorates`, `listCoverageCities` per `docs/plan/api-client-gap.md` line 83). i18n keys exist: `packages/i18n/src/en.ts` `checkout.pickGovernorate` (908), `checkout.pickCity` "Choose a city or district" (909), `checkout.governorate` (931), `checkout.city` (932), `checkout.addressErrors.governorate/city` (944-945).
- ADR-0040 (`docs/adr/0040-gcc-expansion-data-and-currency.md`): Proposed; introduces `market` as a first-class config behind a single `EG` value; money and locale per market. Implication: location ids should be market-scoped (the `EG-` prefix already is).

### Inferences
- The `EG-xx` governorate code and kebab city code are the de-facto stable ids; reuse them rather than inventing new ones.
- There is no seeded district/neighbourhood list, no alias/search column, no `kind` column, and no sort metadata beyond `position`. A district level would be net new.
- Naming drift (`city_code` in DB, `city_district_code` in API, `district` in docs) must be resolved before adding a third level.

### Gaps
- Whether the 27-governorate seed is complete/accurate vs official sources was not verified (fixture comment says "major cities" only).
- `docs/data-model.md` itself only links to module docs; no single ERD node for location reference data exists.
- No outlet-specific (physical shop) table or API found; see Q2.

## Q2. What does the mobile outlet list use today, and what are the minimal changes?

### Takeaway
City is not modelled on the store at all: `StoreSummary` has no location fields; `city`/`country` arrive only through the optional `StoreCardExtras` that DEV fixtures fill with free English strings ("Cairo", "Giza"). A filter needs (a) location fields on the store/outlet model, (b) one new `DirectoryFilter` field and one predicate in the pure `filterStores`, (c) AR-first i18n keys, and (d) a picker sheet reusing the checkout coverage list.

### Cited Findings
- `apps/mobile/src/features/worlds/model.ts` lines 11-26: `StoreSummary { id, name, kind: "local"|"global", status: "active"|"suspended", maxVerifiedDiscountPct, rating, followerCount, liveDrop, trendingRank, newestDropAtMs, deliveryDays, isFavourite }` — no city, governorate or location.
- `apps/mobile/src/features/stores-directory/model.ts` (217 lines): `DirectoryFilter { query, world, verifiedDeals, liveDrop, myStores }` (16-23); `EMPTY_DIRECTORY_FILTER` (25); `normalizeQuery` Arabic folding (36-51); `filterStores(stores, f)` pure predicate (53-63, query matches only `s.name`); `activeFilterCount` (91-93, hard-coded sum of five terms); `StoreCardExtras { city?, country?, hoursText?, distanceKm?, openNow?, closesAt?, photoUrl? }` with comment "Fields the store model does not carry yet" (173-184); `StoreCardView.locationLine` (190); `toCardView` builds `locationLine = [city, country].filter(nonEmpty).join(", ")` (201-207) — free text, no ids, not localised by id.
- `apps/mobile/src/features/stores-directory/StoresScreen.tsx` (180 lines): builds the filter at line 66 (`{ ...EMPTY_DIRECTORY_FILTER, query, world }`), only a search query and world are wired; `hasCities` (69) checks `dev?.extras[s.id]?.city`; renders `v.locationLine` only for the outlets route (140). So today no UI filter sheet for city exists in this screen.
- `apps/mobile/src/features/stores-directory/dev-fixtures.ts`: `devOutletsFixture()` returns null unless `__DEV__` (27-28); three outlets with `city: "Cairo" | "Giza"`, `country: "Egypt"` (33-41). Production comment: "Null in production, where outlet data does not exist yet (honest empty state)" (26). Outlet data therefore does not exist in the backend.
- `apps/mobile/src/features/stores-directory/api.ts`: `ApiStoresDirectoryPort.listStores()` delegates to `ApiWorldsPort` (`GET /v1/stores` via generated `listStores`); comment states the wire has no follow toggle, counts, or verified flag (lines 5-9).
- Tests: `apps/mobile/src/features/stores-directory/stores.test.ts` (137 lines) covers `normalizeQuery`, `filterStores` (hides suspended; world/verified/live/my-stores), `activeFilterCount` (expects 5 for a five-field filter, line ~50 — will need updating), `sortStores`, selection helpers, `toCardView`.
- i18n: mobile uses `@outlet/i18n` (`packages/i18n/src/ar.ts`, `en.ts`, `index.ts`, `localized-name.ts`). Parity gates: `packages/i18n/src/index.test.ts` ("has identical key sets in ar and en", "no empty Arabic strings"); `apps/mobile/src/i18n/keys.test.ts` (every literal `t("a.b")` used in `apps/mobile/src` must resolve; dynamic template keys are tracked separately, so avoid `t(\`...${x}\`)`). `apps/mobile/locales/ar.json`/`en.json` only hold iOS permission strings (NS*UsageDescription), not UI copy. Existing worlds keys live under `worlds:` in `en.ts` (line 482), e.g. `worlds.discountUpTo`.
- Design constraints (`docs/design-system/ux-principles.md`): no developer text/ids/enums in screens (rule 2, enforced by `tooling/copy-lint` and i18n parity); direction follows language, logical start/end (rule 3; Maestro `08-rtl-critical-path`, `tooling/e2e` Arabic runs); 44pt touch targets via kit controls, raw `TouchableOpacity`/`Button` banned by `DS-RN-COMPONENT` (rule 6); Arabic first (rule 11); design-debt baseline `tooling/design/debt-baseline.json` must not grow, `node tooling/design/check-debt.mjs` (lines 22-23). StoresScreen.tsx is a likely debt-baseline file; touching it must not add violations.
- Copy-lint: `tooling/copy-lint/{cli,lint,rules}.mjs`, `allowlist.json`: bans hard-coded numeric social proof. Facet counts shown next to districts must come from the server, never invented ("never fake stock/timers/reviews", CLAUDE.md non-negotiables).

### Inferences (minimal change list, in order)
1. Data type: add optional `locationCode`-style fields to the outlet/store view, e.g. `governorateCode: string | null` and `cityCode: string | null` on `StoreSummary` (or on a new `OutletSummary`, since physical outlets are a separate dev data set). Keep `StoreCardExtras.city/country` as display override only; derive `locationLine` from ids + locale instead of raw strings.
2. Filter: add `governorateCode: string | null` and `cityCode: string | null` to `DirectoryFilter` and `EMPTY_DIRECTORY_FILTER`; in `filterStores` add `if (f.governorateCode !== null && s.governorateCode !== f.governorateCode) return false; if (f.cityCode !== null && s.cityCode !== f.cityCode) return false;` (a city filter implies its governorate; selecting a governorate alone matches all its cities). Update `activeFilterCount` (count location as one filter) and the existing test that expects 5.
3. Search: optionally let `normalizeQuery(name)` matching also test the location names/aliases (AR via the existing folding, EN lowercase).
4. i18n keys (AR first, then EN, same key paths): e.g. `stores.filters.location`, `stores.filters.allGovernorates`, `stores.filters.allCities`, `stores.filters.clearLocation`, `stores.filters.noOutletsHere`; reuse `checkout.pickGovernorate`/`pickCity` wording only by copying, not by cross-feature key reuse (or promote to a shared `location.*` namespace). Location NAMES come from the dataset (`name_ar`/`name_en`), not from i18n files, picked via `packages/i18n/src/localized-name.ts` pattern.
5. UI: a bottom-sheet picker built from kit controls (44pt rows, logical start/end), fed from the same `listCoverageGovernorates`/`listCoverageCities` port that checkout already wraps (`apps/mobile/src/features/checkout/addresses-api.ts`), with an honest empty state when no outlets match.
6. Route params: existing `parseStoresParam`/`shopAllTarget` pattern (model.ts 112-128) shows how to serialise filter state to route params safely (capped, deduped); do the same for `governorate`/`city`, validating against the dataset.

### Gaps
- Not read in full: `StoresScreen.tsx` and `StepScreens.tsx` (only grep). Whether a filter sheet component exists elsewhere (e.g. shop-all) was not inspected.
- Whether `StoresScreen.tsx` is in `tooling/design/debt-baseline.json` was not checked.

## Q3. What API contract exists for stores, and what seams exist for sharing one location dataset?

### Takeaway
`GET /v1/stores` has no location parameter or response field; `StoreSummary` (OpenAPI) has none either. Only legal-identity governorate exists as free text on the store detail path and is flagged as missing from OpenAPI. A shared dataset seam exists in `packages/domain` (pure, import-free), consumed by the API module and migrations; mobile gets it only through HTTP.

### Cited Findings
- `docs/api/openapi.yaml` line 1920 `/v1/stores`, op `listStores`: params `Cursor`, `Limit`, `world` (required: local|global|everything|my_stores), `sort` (trending|biggest_verified_discount|new_drops|fastest_delivery|name). Scope `shopper:catalog.read`, `x-pii-class: P1`, rate limit 120/60s. No governorate/city/facet parameter, no facets in `StoreSummaryPage`.
- `StoreSummary` schema (line 33531): required `id, slug, name (LocalizedText), kind, verified_badge, live_drop, is_favorite`; optional `logo_url, cover_url, max_verified_discount_pct, rating, ...`; `additionalProperties: false`, so adding fields is a contract change requiring regeneration of `packages/api-client`.
- Mobile mapping from wire to `StoreSummary` is in `apps/mobile/src/features/worlds/api.ts` (`ApiWorldsPort`), referenced by `stores-directory/api.ts`.
- Store module domain: `apps/api/src/modules/stores/domain/store.ts` (`Store`, `LegalIdentity.governorate: string`, lines 25-46); module tests `stores.http.test.ts`, `stores.public.http.test.ts`, `stores.http.pglite.test.ts`, `domain.property.test.ts`.
- Seller registration: `docs/specs/sellers-module.md`, `docs/specs/seller-center-web-onboarding.md`, `docs/specs/brand-onboarding.md`, `docs/data-model/sellers.md` line 43 (`governorate` text) mention governorate; they store a free string today.
- Package seams: `packages/domain/src/addresses/` (pure data + `evaluateCoverage`, no infra imports, consistent with dependency-cruiser rule "no infra imports in domain/", master prompt A2.3); `packages/validation` (Zod schemas, `docs` A2.1/Zod at every boundary); `packages/api-client` (generated); `packages/i18n` (strings + `localized-name.ts`); `packages/db` (migrations). There is no `packages/geo`/`locations` package. `docs/specs/stores-worlds.md` does not define outlets or a physical-store entity (grep for "outlet" returned nothing there); the in-store route `/stores/outlets` exists only in mobile `nextRoute` (model.ts 160-164).
- Privacy: coverage endpoints are `x-pii-class: P0`; store legal governorate is P2-at-source but public by law (`docs/specs/stores-worlds.md` line 22, 43). Outlet city/governorate of a shop is a business attribute (P0/P1), not shopper PII; the shopper's chosen filter must not be persisted with identity unless consented (`docs/haul-master-prompt-v3.md` §B1, §26 analytics: no PII in events; location filter ids are non-PII but precise location is not used here).

### Inferences
- Backward-compatible API change: add optional query params `governorate` (same pattern `^EG-[A-Z]{1,3}$`) and `city` (same slug pattern) to `listStores`, plus optional `location: { governorate_code, city_code, governorate_name?, ... }` on `StoreSummary`/outlet, and optional `facets.locations[{code, count}]` on the page schema (counts computed server-side only). Validate params against the coverage tables (400 `unknown_governorate`/`unknown_city`, mirroring addresses spec).
- To avoid a cross-module import (module boundaries via public `index.ts` only), the shared dataset should be consumed by `stores` from the shared package, not by importing `apps/api/src/modules/addresses`.
- Store registration should switch `LegalIdentity.governorate` from free `string` to the governorate code (`EG-..`) with an FK-checked projection, and add outlet `city_code`.

### Gaps
- Did not open `apps/mobile/src/features/worlds/api.ts` or generated client to confirm field mapping details.
- No Stores table DDL inspected (`packages/db/migrations` for stores) — whether stores already have location columns is unverified beyond the domain type.

## Q4. Recommended canonical data model, home, and test plan

### Takeaway
Create one shared, pure location reference package (suggest `packages/domain/src/geo` or a new `packages/geo`) that generalises today's `coverage-data.ts`, keeps existing `EG-xx` and city slugs as stable ids, adds a `kind` enum, optional `district` level, aliases, sort order and coverage flags, and is the single source for seeds, address form, courier coverage, outlet filter and seller/outlet registration.

### Cited Findings
- (Grounding) Existing id formats: governorate `^EG-[A-Z]{1,3}$`, city `^[a-z0-9-]{2,60}$` (migration 0050 lines 25-38); `position smallint` ordering; names `name_ar`/`name_en` with length 1-80.
- (Grounding) Search normalisation to reuse: `normalizeQuery` in `apps/mobile/src/features/stores-directory/model.ts` 36-51 (alef/ya/ta-marbuta folding, tashkeel/tatweel removal, Eastern/Persian digits). Spec §4 requires Franco-Arabic and AR/EN synonyms for search (`docs/haul-master-prompt-v3.md` §4 Engine).
- (Grounding) Expand/contract only migrations (master prompt T3), so new columns must be additive.

### Inferences (recommendation, a proposal not existing code)
Model (single flat table, parent pointer, stable ids):
- `location_areas(id text PK, market text DEFAULT 'EG', kind governorate|city|district|neighbourhood, parent_id text NULL FK, name_ar, name_en, aliases_ar text[], aliases_en text[] (incl. Franco-Arabic, common spellings e.g. "Qalyubia/Kalyoubia"), position smallint, active bool, outlet_filterable bool, courier_coverage via existing courier_coverage table keyed by id, version, valid_from)`.
- Id rules: keep `EG-C`... for governorates and existing city slugs; districts as `<city-slug>/<district-slug>` or a new slug scoped by parent; never reuse or renumber ids (they are persisted in `saved_addresses`, orders, `courier_coverage`). Prefix by market (ADR-0040) so GCC rows can be added without collision.
- Compatibility: expose a view/mapping so `coverage_governorates` = `kind='governorate'`, `coverage_cities` = `kind in ('city')`; district rows map to the data-model docs' nullable `district`. Resolve naming drift (`city_code` vs `city_district_code` vs `district`) with an ADR; safest default: treat the existing "city" as the second level (`city_district_code` in the API already says "city or district").
- Home: pure data + helpers in `packages/domain` (domain layer, no infra imports), exported through its public `index.ts`; API `stores`, `addresses`, `fulfillment`, `sellers` modules import via the package; mobile/web use the generated API client (`/v1/coverage/*`) and may bundle the static list only as an offline fallback verified by a test against the API list. The seed in migrations is generated from this file (as the header of `coverage-data.ts` already intends).
- Filter semantics: outlet filter is by `governorate_id` (exact) and optional `city/district id` (exact); governorate selection includes all descendants; store counts come from the server facet; "covered by courier" is a separate flag and not an outlet-location condition.
- Do not use user's precise location for this filter; use a manual picker (location_precise consent otherwise, §B1).

Test plan:
- Unit (vitest): dataset integrity (unique ids, every city parent exists, AR and EN names non-empty, code regexes, no duplicate normalised AR names within a parent, ids stable against a committed snapshot to catch renames); `filterStores` location predicate (governorate alone, governorate+city, city implies governorate, null = no filter, suspended still hidden); `activeFilterCount`; `toCardView.locationLine` per locale.
- Property (fast-check, already used per master prompt A2.10): filtering is monotonic (adding a filter never grows results), idempotent, order-preserving, and a governorate filter result equals union of its city filters' results; normalised search finds every alias to its own area.
- Contract: OpenAPI additive change + api-client regen check; Pact consumer test for `listStores` with the new optional params; `evaluateCoverage` tests unchanged; migration test (pglite, like `apps/api/src/modules/addresses/kysely-store.pglite.test.ts`) that seeds equal the package data.
- i18n parity: add keys to both `packages/i18n/src/ar.ts` and `en.ts` (`index.test.ts` parity and non-empty Arabic) and use literal keys so `apps/mobile/src/i18n/keys.test.ts` resolves them; run `tooling/copy-lint` (no developer text/ids like `EG-C` in UI).
- RTL and a11y: `tooling/e2e` Arabic run plus Maestro `08-rtl-critical-path` extension (sheet opens, rows mirrored, chevrons mirrored, selected state announced); 44pt targets, accessible names on clear/chevron buttons, VoiceOver reads "Cairo, Nasr City" order in both languages; Dynamic Type; empty state when 0 outlets; `node tooling/design/check-debt.mjs` must pass.
- Authorization: `/v1/stores` is shopper-scoped read; add a negative test (unauthenticated 401) for the new params and a 400 test for unknown codes and oversize input (API4).

### Gaps
- Official governorate/district counts and spellings need an authoritative source (CAPMAS or Egypt Post); not researched here and no source was consulted. Flag VERIFY.
- Whether admin edit of location data (addresses spec says "admin-editable later") needs a dual-approval workflow is undecided.
- Ownership of an ADR for the unified location model: none exists; ADR-0040 is the only related one and is Proposed.
