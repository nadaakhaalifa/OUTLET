# Admin module

Operations: approvals, KYC, relay DLQ replay / discard, reconciliation, audit log (list, verify), PII access log, store suspend / reinstate, feature flags and kill switches, just-in-time elevations.

## Audit-log verify and elevations
- `GET audit-log/verify` (`audit.read`, 6 per minute per staff user): `PgAuditStore.verifyChain` through the SECURITY DEFINER page function as `outlet_app` (no admin-only role needed). A broken chain answers 200 with `ok:false`, `broken_seq`, `reason`. A truncated tail needs the external seal (`audit_seals`), not covered here.
- `GET/POST elevations`, `POST elevations/{id}/decision` (`elevation.request` / `elevation.approve`): all writes go through `@outlet/admin-access` (audited in the same transaction, idempotency key required). Approvers see every elevation of the market; others see their own.
- `super_admin` (break-glass) cannot be approved here (409 `dual-approval-required`): it activates when its approval request (`approval_request_id`) gets two votes on `approval-requests/{id}/decision`; the last vote runs `activateElevation`.
- Composition: `ops.elevations` (`PgElevationReader`) must be added to the production wiring in `src/cli.ts`; until then the three elevation routes answer 503 (fail closed). Not done here because cli.ts is being edited by another agent.

## Refunds, payouts, returns, disputes: reader mechanism
No migration, no new grant, no SECURITY DEFINER function: `PgOpsLists` reads as the worker jobs that already own the tables, market pinned by the policy and by the SQL (`app.job()` + `market_id = app.current_market_id()`). Refunds, returns and disputes run as `finance.refunds` (SELECT policies `*__worker_finance_refunds`, migration 0019), payouts, payout lines and holds as `finance.payouts` (FOR ALL policies from 0018, so the same context also serves hold and release through `PayoutService`). `reporting.rollup` / `admin.dashboard` also have SELECT on these tables but are the rollup's own jobs and are not used for request-time lists. This is the `PgReconciliationReader` mechanism (worker job under ADR-0011), not the `pii_access_log_list` SECURITY DEFINER function, because the tables are market-pinned and the job policies already exist. Without `DATABASE_URL_WORKER` the whole console is 503, so these routes fail closed with it; `ops.lists` / `ops.payouts` absent = 503 `admin-unavailable`. In `cli.ts` the `PayoutService` is built with `UnconfiguredPayoutRail` and `UnconfiguredPayoutDestinations`: hold and release never touch the rail, so no money can move from this path.
List order is `(created_at, id)` DESC. Migration 0042 adds the matching `(market_id, [status,] created_at DESC, id DESC)` indexes (partial for the open pipelines on payouts, return_requests and disputes), so deep pages are index-ordered. Production creates them with `CREATE INDEX CONCURRENTLY`.
Payout store names are not returned (store id only): `stores` has no `finance.payouts` policy; a name join needs a new policy or the dashboard-style rollup.

## Dashboard
`DashboardService` (`dashboard.ts`) authorizes each tile with `authorize(principal, tileAction, admin_console)` before any read, then runs the reads together (`Promise.all` over per-read try/catch: one failing read only affects its own tiles). Sources: `PgDashboardReader` (rollup tables, worker job `admin.dashboard`, migration 0035; written by `@outlet/reporting` job `reporting.rollup`), `PgKycAdmin.count`, `PgApprovalReader.countPending` (excludes own requests, requests already voted and actions the caller's roles cannot decide), `PgElevationReader.countActive`, `AttentionAdmin.countOpen`, `FlagAdmin.list`. Composition: `ops.attention` and `dashboard` in `cli.ts`; each missing piece degrades to `not_connected` for its tiles only (the routes for attention answer 503 until composed). The rollup tick (`reporting.rollup_requested`, scope sales / nightly / snapshots) is registered in `src/worker-consumers.ts` (`reportingRollupHandlers`); the scheduler that emits it belongs to the worker process. See ADR-0015.

## Store suspend / reinstate: how the second vote executes
The last approver's vote (or `POST approval-requests/{id}/execute` for recovery) runs, in this order: `access.verifyApproved` (read-only: APPROVED, unexecuted, unexpired, hash intact, role held) -> `StoreModeration.apply` (acts only on `payload.storeIds`, the set pinned at filing; 409 `invalid-transition` before any write when the store is no longer in the allowed state; `verifyApproved` also refuses within 60 s of expiry) -> `access.executeApproval` (claim + audit entry `store.suspended` / `store.reinstated` via `AuditPort.appendIn(tx)`).
`apply` cannot share the claim transaction (it runs under other DB roles), so it is split into idempotent effects that run before the claim:
1. `SellerOnboardingService.suspendStore` / `reinstateStore` (store id -> seller id lookup inside the `seller.kyc` job tx; KYC case APPROVED <-> SUSPENDED, `sellers.status`, outbox `seller.suspended` / `seller.reinstated`). Already in the target state = no-op, no second event.
2. `StoreService.setModerationStatus` for every live store of that seller (stores.status, the published read model, outbox `store.status_changed`). Suspending deletes the store and its listings from `catalog_public_*` (this is what hides them); reinstating re-projects the store and its published listings (bounded to 5000).
If the claim or audit fails after the effects committed, the request stays APPROVED and the execute route converges.
Gaps (reported, not invented): nothing consumes `seller.suspended` yet (the old comment "catalog and payouts react" was not true), so payouts are not held by a suspension, orders in flight and open reservations are untouched, and a VACATION store comes back as ACTIVE (no column keeps the prior status). Price enforcement's `suspend_store` ladder step still only emits `payouts.hold_requested`; it does not use this path. Stores that are draft, in review or closed are skipped when a seller is suspended.

Not served yet (need a design decision or no contract): staff list (no staff directory table; email/name are encrypted `users` columns), privacy/tax/price-integrity consoles (no readers yet), user lookup (not in the contract; needs an admin-context read of `users` or a SECURITY DEFINER function and the phone last-2 digits only exist inside `phone_ct`, so it needs the field cipher and a reason-coded `pii_access_log` row: left out deliberately).

`GET audit-log/verify` stays a GET (the console BFF must call it with GET). `store_sales_daily` (per store, P2 for sole traders) is read only by the `admin.dashboard` job and never reaches seller-visible or export paths.
