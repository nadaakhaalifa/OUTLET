# @outlet/payouts

Seller payouts and finance reconciliation (P1-19). TWO-KEY area: owner approval and a fresh-context chief-reviewer sign-off before merge.
Specs: master prompt T4, `docs/specs/ledger-chart-of-accounts.md` 4.1, 4.3, 4.11 and invariants I11, I12, I21-I23, `docs/data-model.md` 7.15-7.17. Migration `0018_payouts_reconciliation.sql`.
Nothing here moves real money: `PayoutRailPort` and `PayoutDestinationPort` have fail-closed Unconfigured adapters (ADR-0029); V3, V41 and V63 gate real use.

## Flow (funds flow `collect_payout` only)
1. `order_group.paid` -> PENDING accrual per seller order (`AvailabilityMover.onOrderGroupPaid`).
2. `seller_order.closed` -> ledger `line_closed` (Dr seller_pending / Cr seller_available) and the accrual is AVAILABLE, eligible at `closed_at + 3 days` (`onSellerOrderClosed`).
3. `PayoutService.buildCycle(market, now)` (weekly, Africa/Cairo): payout per store = eligible accruals + a signed netting line (refunds, chargebacks after earlier payouts). Debt carries forward.
4. `approve` (finance; dual approval at or above the threshold through `@outlet/admin-access`) -> `send` (ledger `payout_sent`, rail call keyed `payout:{id}:{attempt}`) -> `settle` (`payout_settled`). A rejected send is reversed and parked ON_HOLD.
5. `SettlementImporter` (PSP files) and `CodRemittanceImporter` post `clearing_settled` / `courier_remitted`; `ReconciliationJob` turns anything unmatched into `reconciliation_exceptions` (escalated after 3 days); `IntegrityJob` checks trial balance, hash chain and projections.

## Decisions
- No ledger hold row for a scheduled payout (the chart has no such kind): the accrual claim plus the balance re-check at SEND (I12) is the guard.
- The payout amount is `seller_available` minus closed-but-not-yet-eligible accruals, not the raw balance, so a store never receives money still inside the grace window.
- Writes run as `outlet_worker` in jobs `finance.payouts` and `finance.reconcile`; sellers read their own rows through store RLS (`listPayoutsForStore`).

## Contracts and review findings (chief-reviewer round 1)
- **Attempt-scoped failure (B1).** `PayoutService.fail(market, id, code, { providerRef, sendAttempt })` applies only to the payout's current attempt and provider reference; anything else throws `STALE_ATTEMPT` (a late bank return for attempt 1 can never reverse attempt 2). A replay of an already applied failure is a no-op. `send` clears `provider`/`provider_ref` when it starts an attempt, so a retry after a timeout never mistakes the previous attempt's reference for this one.
- **Dispute holds (B2).** `DisputeHolds.onDisputeOpened` / `onDisputeResolved` consume `dispute.opened` / `dispute.resolved` through the inbox and write `payout_holds(reason='dispute', seller_order_id, source_ref = dispute_id)`; eligibility already honours holds. Unique `(source_ref) WHERE reason='dispute'` makes re-emission harmless, and a `resolved` that overtakes its `opened` leaves a released tombstone. The Zod payload `DisputeEventPayload { seller_order_id, store_id, market_id, dispute_id }` is exported from `@outlet/payouts` for the returns module (emitter) to import. A dispute id opens once: a reopened dispute must carry a new id.
- **Two-commit window in `completeApproval` (B3).** `executeApproval` runs on the app connection (outlet_app) and `markApproved` on the worker connection, so they cannot share a transaction. If the process dies between them the request is consumed but the payout is still SCHEDULED. The retry sees `{executed:false, reason:'already_executed'}` and resumes only when `deps.readApproval(requestId)` returns an APPROVED `payout.approve` request whose `targetId` is this payout. With no reader configured it fails closed (`APPROVAL_NOT_READY`; file a renewed request with `approve(..., { renew: true })`). Production wiring must supply `readApproval`.
- **Ledger posting allow-list (B4).** outlet_worker may INSERT into `journal_entries` / `postings` only in jobs payments.webhook, checkout.expiry, finance.payouts, finance.reconcile and finance.refunds. Enforced by BEFORE INSERT triggers `journal_entries__worker_post` / `postings__worker_post` (migration 0016), not by RLS: the ledger tables have no tenant key, enabling RLS would need outlet_app policies that the ADR-0011 audit does not permit, so a trigger scoped to `current_user = 'outlet_worker'` is the least invasive equivalent. Flagged for the chief reviewer.
- **`seller_order.closed` emitter contract (B5).** `amount_minor` (decimal string of piastres still sitting in `seller_pending` for that order, i.e. net of anything refunded while pending) is REQUIRED. A message without it fails with `INVALID_INPUT`, the inbox row rolls back, and the relay sends it to the DLQ after its retries; it is never defaulted. The orders close job (next task) must emit it; `SellerOrderClosedPayload` is exported.
- **PSP netting of refunds (B6, V4 assumption).** Under `collect_payout` a refund after payout reaches `seller_available` as a negative adjustment and is netted from the next payout; the PSP is assumed to net refunds out of its settlement to us (V4, unverified), so the refund does not need separate cash from the platform. The COD remittance importer's credit side (the courier's cash into `cod_clearing`) is expected from orders task 4.3; until then COD remittance lines match only what orders has already posted.
- **Mutation testing.** `pnpm mutation` (StrykerJS, vitest runner) targets `src/domain/netting.ts`, `src/domain/eligibility.ts` and `src/application/payout-service.ts`; break threshold 80.

## Ledger integrity: incremental chain verification
`IntegrityJob` (worker job `finance.reconcile`, consumer `finance.integrity`) verifies the hash chain forward from a cursor stored in the latest `ledger_integrity` run's `details` (`verified_through_seq`, `cursor_hash`, `complete`, `full`), in pages of 10,000 entries, each in its own short transaction, within a per-tick budget (`WORKER_INTEGRITY_BUDGET_MS`, default 8 s). An unfinished run is `running` and re-emits `ledger.integrity_requested` with a `continuation` number until the head is reached; the trial balance and other checks run on the last tick. A broken link anywhere in the verified range fails the run (`chain_broken`, `ledger.integrity_failed`) and the cursor stays before it.
Trade-off: between full passes history behind the cursor is trusted. Tampering with already-verified entries is caught only by the weekly full pass (scope `ledger_integrity_full`, Friday 01:00-06:00 Cairo, cursor reset to 0), at most 7 days later; tampering with new entries is caught the same night. See ADR-0016.

## Trial-balance index (migration 0042)
`postings (market_id, currency) INCLUDE (amount_minor)` lets the nightly per-currency trial balance run as an index-only scan. Cost: one extra index entry (about 20 bytes) and WAL per posting insert on the highest-volume append-only table; autovacuum must keep the visibility map current for index-only scans to pay off. Production builds it with `CREATE INDEX CONCURRENTLY`.
